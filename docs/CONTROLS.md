# The control contract

**Scope:** every class the markup puts on something a person can click, type into or focus. 42 of them today.
**Why this document exists:** three bugs reached production in one week — the close cross under a filter chip, the score under the star on every poster, the blue box around the page title — and all three were the same failure. The component was built for the one state somebody happened to be looking at, and met a second state in the wild.
**Draft by Claude, 2026-11-25. Edit or reject by number.**

Numbers are from `npm run states`, which reads the markup and the stylesheets and reports what each control actually styles. Run it before arguing with a figure here.

---

## C1 — What a control owes

A control is unfinished until every line below is answered for it. "Answered" includes *deliberately nothing* — but written down, not left out.

- **C1.1** **Rest.** How it looks doing nothing.
- **C1.2** **Hover.** Pointer feedback. Was 19 of 42 styling none; now 5, and all five are answered by an ancestor — `.bd` and `.th` sit inside `.srow`, `.lfind-in` inside `.lfind`, and `.scrim`/`.sheet` are `<div>` containers rather than controls. A state drawn on a subtree counts: `.tile:hover .art` is a hover.
- **C1.3** **Focus.** Keyboard feedback. See C3.
- **C1.4** **Active.** The moment of the press. Answered once, product-wide, scoped the way the focus ring is: `:is(button, [role="button"], a[href]):not(:disabled):active { transform: scale(.97) }`. A control that must not move overrides that one rule. `transform` rather than a colour step because it is the only answer that works on a filled button, a ghost button, a chip and a poster without knowing what any of them look like.
- **C1.5** **Selected / pressed**, if it is a toggle. See C4.
- **C1.6** **Disabled**, if it can ever be disabled. Not "greyed out by opacity" — opacity on a filled control also fades its border and its shadow, and the result reads as a rendering fault.
- **C1.7** **Busy**, if it can be waiting on the network.
- **C1.8** **Invalid**, if it accepts input.

## C2 — What a control must survive

States are half of it. The other half is content, and it is the half that broke twice this month.

- **C2.1** **With an icon and without one.** `.icon` is `display: block`. A control that holds an icon beside anything else declares a flex or grid context, and thereby says which direction it runs. Enforced: `verify` check 17.
- **C2.1a** **An icon *alone* in a box is not covered by that check**, which only fires when the icon has a sibling. A lone glyph needs a correctly *sized* box as well as a correctly declared one, and it passed all 17 checks while sitting 2px right of centre. Geometry is not checkable by reading CSS — it is checkable by measuring a rendered control, which is C9.
- **C2.2** **The longest label it will really get.** Not "Action" — "Action & Adventure", TMDB's longest genre name, and the Hindi for it. **Drawn and checked** since 2026-11-26: specimens carry a `content` axis beside their `states`, and `gallery:audit` fails on it. Every string in it is real — the 70-character title and the Hangul one are lifted out of `snapshots/tmdb-fixtures.json.gz`, the product's own recorded TMDB responses, and the Devanagari is there because `facets.js` leads with Hindi, Tamil and Telugu. The rule for adding one: it must be content the product will really hold. An invented 200-character string proves a control *can* be broken; it does not prove anything *will* break it.
- **C2.2a** **And the shortest it will really get.** The long end wraps; the short end has its own failure, and it only appears once a control has a `min-height` — see C14. The product's shortest chips are not genre names at all: the region chips are ISO country codes (`IN`, `US`, `GB`, from `browse.js` REGIONS) and Library's tablist ends in `All`. Both are drawn now. Nothing had ever asked a control to survive being *short*.
- **C2.3** **One child and several.** A chip with a count, a chip with a count and a cross.
- **C2.4** **Both themes.** Light is not dark with the numbers flipped: a floating surface gets *lighter* as it rises in dark and *darker* in light, which is why `--raised` exists and cannot alias the ink scale.
- **C2.5** **All three bands.** 390, 900, 1280. The 900 band is the one nobody draws.
- **C2.6** **Empty, one, and many**, wherever it renders a list. **Drawn and checked** since 2026-11-26 — see C11.

## C3 — Focus has exactly one owner

Today it has three, and that is the blue box around the page title.

- **C3.1** The global ring in `shell.css` is the default and should stay. **40 of 42 controls rely on it** — that is fine, that is what a default is for.
- **C3.2** **The global ring applies to controls only.** It currently matches anything focusable, including the `<h1>` that `Navigation.jsx` focuses on every route change so a screen reader announces the new page. That heading is a destination, not a control, and must not be drawn as one. Scope the selector to real controls.
- **C3.3** **No component uses bare `:focus`.** `:focus` fires on a mouse click and stays after it. `.searchbox` and `.inp` both do this today, which is why clicking the search field leaves a ring behind. `:focus-visible` is the only correct spelling.
- **C3.4** A component overrides the global ring only when the default is genuinely wrong for it — an inset ring on a field that sits flush in a bar, for instance — and then it styles `:focus-visible`, not `:focus`.

## C4 — One state, one spelling

- **C4.1 Answered.** **Selection is an ARIA attribute, never a class.** The attribute is the one the control's role requires: `aria-pressed` for a toggle button, `aria-selected` inside a tablist, `aria-current` for the link to the page you are on — React Router writes that last one itself (measured: `NavLink` emits `aria-current="page"` exactly when active, alongside the `on` class that was redundant beside it). The stylesheet selects on the attribute, so **a selected look is unreachable without the announcement that goes with it.**
- **C4.2** It had two spellings, and that is how the Kind filter looked unselected for as long as it existed: `.seg.on` was the only rule drawing a selected segment, and `FilterPanel` set `aria-pressed` and never added the class.
- **C4.3** **The other twelve controls wrote both, agreeing — and that is why nobody saw the one that didn't.** Writing both is not a safety net; it is two chances to be wrong, and twelve matching pairs made the pair look like the convention. Deleting the class was therefore the fix, not adding it to the thirteenth.
- **C4.4** `.on` is forbidden outright rather than kept as a synonym, because **it meant three different things**: selected (ten controls), a lit star in the 10-point rating (now `.full`, beside `.half`), and the library's find row being open (now `.finding`). One class name, three meanings, and no reader could tell which from the name. `.sw.on` was a fourth case — a class written at the call site that **no rule had ever matched**; the attribute was doing the work alone.
- **C4.5** **`role="tab"` with `aria-pressed` was a live defect.** Library's shelf filters are a tablist, and `aria-pressed` is not an attribute that role defines — so the state was announced with something a tab does not have. `shared/ui/selection.js` picks the attribute from the role, and both stylesheets select on `:is([aria-pressed="true"], [aria-selected="true"])`, so getting it right costs nothing visually. `:is()` takes the specificity of its most specific argument, so every converted rule stayed at the specificity it had — no cascade drift anywhere.
- **C4.6** Held by `verify` check 21, which forbids ten class names that have ever meant "selected" in CSS selectors and in `className`, and fails if fewer than ten rules select on a selection attribute — because a check that cannot find what it counts passes forever. Proved both ways: reinstating `.ptab.on` in the CSS while the JSX wrote `aria-selected` (the exact Kind-filter shape) was named by file and line, and stripping all 21 selection rules from the stylesheets tripped the counting guard.
- **C4.7** **Measured inert**: 22 selected looks × 13 paint and box properties, old spelling against new, read from the stylesheets at `HEAD` and in the working tree in the same run — **286 of 286 identical**. Proved the measurement fires by reinstating `.ptab.on`, which it caught as the selected tab losing its accent colour and its underline.

## C5 — Where a control lives

- **C5.1 Answered.** A control used by more than one module belongs in `src/shared/ui/`. **Four were not there.** `.btn` was declared in three layers at once; `.circ` (entry, profile, title, library, search), `.sect-h` (title, search, profile) and the `.btn-lg`/`.btn.ghost` variants were in the journeys or module layers. `.sect-h` was the sharpest case: the control lived in `src/app/shell.css` while its `.markrow` variant lived in `ui.css`, so **neither file showed the whole control.** All of it is in `ui.css` now.
- **C5.2 Answered.** **A module never restyles a shared control. 0 are repainted from another layer**, down from what `states` reported as 7. The real number was never 7 — see C5.6.
- **C5.3** If a module needs a shared control to be different, the difference is a **variant on the shared control, declared where the control lives.** Eight moved: `.chip.applied`, `.btn-lg`, `.btn.ghost`, `.circ.sm`, `.sheet.editor`, `.sheet.tall`, `.linkish.back`, `.chips.aside`, plus `text-decoration: none` on `.chip` and the new `.skel-block`. Where a variant is *used* is not where it is declared.
- **C5.4** **A module may *position* a shared control; it may not *repaint* it.** Position is how much room the control gets — `width`, `height`, `margin`, `padding`, `display`, `overflow`. Paint is what it looks like — `background`, `color`, `border`, `border-radius`, `box-shadow`, `font-weight`, `opacity`, `filter`, `letter-spacing`. The three remaining cross-layer rules are all position: `.card.signup .btn { width }`, `.nothing .btn { margin-top }`, `.tside-inline .prow { max-width }`, `.topbar-in .circ { margin-right }`, `.routewait .skel-block { height }`.
- **C5.5** **A parent may set a custom property the control itself declares.** That is the sanctioned way for a context to influence paint: the control still decides what to do with the value, and the knob is visible in the control's own file. `--sheet-pad` already worked this way; `--prow-bg` and `--noart-size`/`--noart-pad` were added by this sweep. **The knob must be a `var()` fallback, not a declaration on the control** — a custom property set on an element beats the same one inherited from an ancestor, so declaring `--prow-bg: var(--surface)` on `.prow` silently broke title's sidebar. Measured as `rgb(247,248,251)` becoming `rgb(239,241,246)`; reading the CSS would not have caught it.
- **C5.6** **`states` had been under-reporting this the whole time, and the fix was check 22.** `states` only ever sees classes that have a *state* rule — a hover, a disabled, a selected — so `.noart`, `.skel-flat`, `.chips`, `.sect-h` and the six `.st-*` tone classes were invisible to it. It said 6 while there were 17. The machine check, which reads every rule, found the other eleven on its first run.
- **C5.7** **Its single count could never reach zero, which is why nobody chased it.** It added together parents positioning children (allowed, and always present) and modules repainting controls (the violation), so the number had a floor of about three and read as "roughly fine, forever". It is two numbers now: *repainted* — which is gated by check 22 and is 0 — and *positioned*, which is informational and is 3.
- **C5.8** **Three of the eleven were the same duplication in different clothes**, and all three say the same thing about class-name conventions:
  - **`.sw` was repainted from `title.css` and `person.css` with the identical two declarations**, written separately, each carrying a comment explaining why reaching into a shared control was acceptable *there*. Every `.sw` in the product sits inside one of those two rows, so the pill was never a variant — **the base was wrong and both modules had been correcting it in private.** The gallery meanwhile drew the bare base, a look that appeared nowhere on screen.
  - **The cover had its own copy of the glass.** `.cover-theme .circ` in `entry.css` was byte-for-byte `.circ.on-image` in the shell — four declarations, the same material, invented twice, neither file aware of the other. Measured identical before removal. `ThemeToggle` takes `onImage` now, so asking for the variant is the only way to get it.
  - **`profile.css` re-derived the status tones.** Six rules, one per status, each naming a `--st-<name>-9` token — a second copy of the map `ui.css` already keeps, where `.st-want` sets `--stl: var(--st-want-9)`. Reading `--stl` is **one rule**, and a seventh status would no longer have to be added in two places.
- **C5.9 Measured inert**: 36 looks × 24 paint and box properties, old stylesheets read from `git show HEAD:` in the same run — **864 of 864 identical**. End to end, `snap` reports `geometry` and `elements` unchanged on all 72 screens; `hash` moves on the 6 cover screens only, which is the `on-image` class being added, the one deliberate markup change. The measurement was proved by dropping `.circ.sm:disabled`'s opacity, which it caught as `0.4 -> 1`.

## C6 — A control is a component, not a convention

- **C6.1** **Answered.** `src/shared/ui/Button.jsx`, `Chip.jsx` and `Segment.jsx` own the markup of the three controls that were class names applied by hand — `.btn` at 45 sites across 19 files, `.chip` at 9 across 4, `.seg` at 3 across 3. Nothing owned them, so a case solved in one file was unknown to the rest, which is precisely how a chip grew a close icon no stylesheet had been told about.
- **C6.2** **It is held by check 19**, not by discipline. A `className` containing `btn`, `chip` or `seg` anywhere outside the three component files fails `verify`, and the message names the prop to use instead. Proved by hand-writing `className="btn quiet"` back into `Picker.jsx`, which it caught by file and line. A control's name used as a *modifier* — `chips`, `pchip`, `fchip`, `filterbtn` — is a different class and is not matched.
- **C6.3** **Writing the components found three bugs that reading the CSS had not.** Each had survived because it required holding two or three files in mind at once:
  - **The Kind filter never looked selected.** `.seg.on` was the only rule that draws a selected segment, and `FilterPanel.jsx` set `aria-pressed` and never added the class. A screen reader announced the state correctly; nobody's eyes could see it, for as long as the control had existed. `selected` is now one prop that writes both spellings.
  - **The chip had two selected appearances, and a third nobody designed.** `ui.css` drew `[aria-pressed="true"]` as a solid fill; `search.css` drew `.on` as a soft tint. Both are 0,2,0, so *which one won was decided by CSS chunk order* — `.on` shipped in the lazily-loaded search chunk and therefore won on the search route by accident of bundling. An element carrying both measured as **neither**: the tint from `.on`, the inset highlight from `aria-pressed`. The first draft of `Chip.jsx` wrote both, and would have shipped that third look everywhere. They are now two named roles, one spelling each, because they were never the same idea — `selected` is an option you turned on, `onRemove` is a filter you take off, and a remove button was never "pressed".
  - **A ninth chip site existed that the inventory grep had missed.** `SearchPage.jsx:259` renders a chip inline inside a sentence; the line also contains `said.chips`, so a `grep -v chips` filter meant to drop the container class hid the control. Check 19 found it on its first run. The machine check caught what the hand inventory did not, which is the entire argument for having it.
- **C6.4** **The component layer made `npm run states` under-report, and that had to be fixed with it.** `<Button className="filterbtn">` renders `class="btn filterbtn"`, so a reader that sees only `filterbtn` concludes the control has no hover — which is what the tool reported for `filterbtn` and `epmark` the moment the migration landed, for two controls that inherit `.btn:hover` and always did. `states.mjs` now restores a component's base class and reads the props that stand for one (`variant`, `size`, `block`, `busy`, `selected`), and `AS` knows the three components render `<button>` by default, without which `.chip` and `.seg` read as unfocusable. See C7.2: this is the fourth time this tool has read too narrowly.

## C13 — There is one toast, and it is raised one way

- **C13.1** `ToastProvider` was built to settle SH15 — "the same action reporting differently depending on where it was done is how one piece of furniture owned by two modules ends up meaning two things." **It landed, and Library and Title went on rendering their own.** Three `<Toast>` elements were mounted at once.
- **C13.2** **They do not queue.** `.toast` is `position: fixed` at one coordinate. Measured on a 390px screen, two of them land in the same **358×48 box at (16, 732)** with the same `--z-toast`, so the later one in the DOM is drawn over the earlier, and `elementFromPoint` at the centre returns the later one — the provider's, because it renders after its children. **You read one message and your tap undid the other action.**
- **C13.3** Library also spelled the action `undo:` where everything else said `actionLabel` + `onAction`, translating it at its own call site. That call site was correct, so the Undo worked — but two spellings for one prop is the C6.3 defect one level up: a prop contract that nothing enforces. Both modules now go through `useToast()`.
- **C13.4** **The one message shape that must carry a way back was the one that did not.** `Title.jsx` reported "Season N cleared" — every tick in a season thrown away — with a dismiss cross. It now carries an Undo, restoring the list it was handed.
- **C13.5** Held by `verify` check 20: one mount point, in the provider, and no `undo:` anywhere. Proved by reinstating both halves, which it named by file and line. **Its "counting nothing" guard earned itself on the first run** — the detection regex required a character after `<Toast`, and `<Toast` is the whole line when the props are indented below it, so it found nothing and the guard said so.

## C7 — How this is held

- **C7.1** `npm run verify` — 22 machine checks, CI-gated. Check 17 is C2.1, check 18 is C12, check 19 is C6.2, check 20 is C13.5, check 21 is C4.6, check 22 is C5.4.
- **C7.2** `npm run states` — the coverage table. Not a gate: the gaps are design decisions and which ones matter is not a machine's call. It has been wrong twice, both times by reading too narrowly — once reporting MISSING focus for 40 controls the scoped global ring covers, once reporting MISSING hover for every control that answers on its subtree, and once filing `:hover:not(:disabled)` as a variant's hover because it counted the pseudos inside `:not()`. A tool that under-reports is worse than no tool, because the clean rows are believed.
- **C7.3a** **`snap` carries two hashes now, and conflating them wasted an afternoon.** `hash` includes each element's class list, so it moves when a class is *renamed* even though nothing moved on screen — the selection sweep changed a class on twelve controls and all 36 screens' hashes changed, which reads exactly like a product-wide layout regression and was not one. `geometry` is the same boxes with the class list left out, and that is the question worth gating: **0 of 72 differ** across the sweep, with `elements` also 0 of 72. Proved the geometry hash is not vacuous by adding 8px to the tab bar's padding: it fired on the two 390px widths and correctly *not* at 900 or 1280, where `.topbar` replaces the tab bar.
- **C7.3b** **No search screenshot contains a chip.** Found while proving the above: 4px of chip padding moved geometry on 6 of 6 library screens and 0 of 6 search screens. The applied-filter chip — the control whose cross dropped to a second line in production — is in no snapshot, because the photographed search screen has no filter applied and `.chips:empty` is `display: none`. The chip is covered by snap only through Library's shelf row.
- **C7.3** `npm run snap` — 72 screenshots, 7 screens × 3 bands × 2 themes. **It photographs the default state only.** None of this month's three bugs would ever appear in it, because states do not show up in screenshots of pages. Its `fingerprints.json` was the end-to-end proof that the 45-site `.btn` migration changed nothing: 72 of 72 identical. **But that fingerprint is structural, not pixel** — element count and geometry hash — and the proof of that is in the file itself: the dark and light shots of a screen share a hash, so only 36 of the 72 values are distinct. It would not catch a colour change. Colour was covered separately, by reading computed styles.
- **C7.4** `npm run gallery` — `docs/as-built.html`, every control drawn in every state it owes. Two things keep it from drifting away from the product, which is how every gallery dies: the CSS is the product's own, inlined verbatim and never restated; and `:hover`, `:focus-visible`, `:active` and `:disabled`, which markup cannot force, are *derived* — each rule that styles one is duplicated with the pseudo-class swapped for `[data-force~="…"]`. A control with no rule for a state draws the same as rest, so the gap is visible rather than inferred. Icons come from the real `Icon` component through vite-node, so one dropped from the role map disappears from the gallery too.
- **C7.5** `npm run gallery:audit` — reads back the computed style of all 60 cells in both themes and reports any state whose paint is identical to rest. It found six on the first run, and it found two false positives in `npm run states`: a state styled only on a variant (`.circ.sm:disabled`) or behind another pseudo-class (`.searchbox:-webkit-autofill:hover`) was being credited to the bare control. Two tools that disagree are worth more than one that is confident.
- **C7.6** `npm run shot -- <control>` — pulls one row out of the gallery at 3×. The gallery is 18,000px tall; a 24px control cannot be judged at the size it ships at, and "looks fine" at 1× is how a 2px offset survives. `--list` names every row, `--light` switches theme.
- **C7.8** **CI now runs the measurements, not just the structural checks.** It ran `verify`, `build` and `test:api` — so for a month the only thing between a measured bug and `main` was somebody remembering to type `npm run check`. All three of the bugs that reached production this month are caught by `gallery:audit` and by nothing in `verify`. CI now also runs `lint`, `gallery`, `gallery:audit` and `states`, with Chromium installed. **Proved the way C7.7 demands:** `gallery:audit` exits **1** when `.chip`'s `display: inline-flex` is reverted to `inline-block` — the actual production bug. `states` is deliberately not a gate and always exits 0; it is in CI for the table in the log, and it blocks nothing.
- **C7.9** `git diff --exit-code docs/as-built.html` after regenerating is also a gate now. The gallery is generated and committed, and verified deterministic — regenerating twice produces no diff. If a PR moves it, the committed copy was stale, which is how a gallery stops describing the product and becomes decoration.
- **C7.10** **Three checks reported the wrong line number, and the cause was shared.** They stripped comments from a file and then counted newlines in the stripped text — and these stylesheets are half commentary, so the answer was off by dozens of lines. `blankComments` replaces each comment character with a space and keeps every newline. A check that names the wrong line is worse than one that says nothing: the reader goes to the wrong place, concludes the check is broken, and stops reading it.
- **C7.7** A new check is proved by reverting the bug and watching it fire. **Three checks in this repo have now passed while broken**, and only re-breaking the product found them: the content check compared a long label to a short one and measured a difference of zero because both were broken; the spec-drift check ran *after* its own results had been collected, so its failures were never read; and `states` under-reported for two separate reasons. A check that has only ever seen a clean tree is not evidence of anything. A check that has only ever seen a clean tree has not been tested. The geometry check in C9 was proved this way: with the reset removed it reported `quickadd 2.0px right`, which is the figure measured by hand before the fix.

## C8 — Artwork has no theme

A control that lands on a poster or a still cannot borrow the page's surfaces, because what is underneath it is a photograph in light mode and a photograph in dark mode. It carries its own ground.

- **C8.1** **That ground is one material, named once.** `--glass`, `--glass-hv`, `--glass-line`, `--glass-blur`, `--on-glass`, in `tokens.css`, outside both theme blocks on purpose.
- **C8.2** It was seven controls inventing it separately: rest opacities `.55 .6 .6 .62 .68 .72`, hovers `.72` and `.78`, and two different base colours — `rgba(8,12,20)` for `.quickadd` and `rgba(4,6,12)` for the other six. The top-right and bottom-left corners of the same poster were built out of different glass, which is a thing nobody can see as a bug and everybody can see as cheapness.
- **C8.3** **The hairline is not trim.** A dark control on a dark poster has no edge of its own. `--glass-line` is what stops it dissolving into the artwork, and it belongs to every glass control, not just the one that happened to have it.
- **C8.4** `--scrim-wash` is a different job — the full-screen dim behind a sheet — and keeps its own name even at the same value. `.tplay-b` was using it as a control ground; it now uses `--glass`.

## C12 — The specification and the code agree, and that is checked

- **C12.1** `docs/design-system.html` is what the design **says**; `src/shared/theme/tokens.css` is what the product **does**. They share 83 custom properties and every one currently matches.
- **C12.2** It is a check rather than a note because the failure is silent and expensive: an agent reads the spec, builds to a value the code no longer holds, and nobody finds out until it is on screen. Neither file is wrong in that situation — they simply stopped being the same file, and nobody reads 162 tokens across two documents to notice.
- **C12.3** One level of `var()` is resolved first, because the code legitimately aliases where the spec states a literal — `--sh: var(--shadow-raised)` and the shadow written out are the same shadow said two ways. Proved by changing `--beam-9`: it reported both `--beam-9` and `--acc`, which aliases through it.
- **C12.4** Only the spec's `<style>` blocks are read. An inline `style="--c: …"` in one of its own demos is local to that demo, not a statement about the system.
- **C12.5** **The specification does not declare the spacing or radius scales**, so those are not cross-checked and `tokens.css` is their only statement. Worth closing, and worth knowing until it is.

## C11 — An item's size does not depend on how many are beside it

- **C11.1** A collection is a third kind of case, after what a control is *doing* and what it is *holding*. Specimens carry a `collection` with `counts`, and the gallery draws each count.
- **C11.2** **The invariant is that an item's size must not change with the count.** That is the signature of the two classic collection bugs: `grid-template-columns: repeat(auto-fit, …)` stretches a lone tile across the page, and a flex child that can grow turns two posters into two half-screens. Both are one word away from true in any stylesheet.
- **C11.3** This product gets both right already — `.grid` is `auto-fill`, `.rail > *` is `flex: 0 0 auto` — **which is exactly why it is worth pinning.** Proved by flipping `auto-fill` to `auto-fit`: one search result became 844px wide and 1302px tall, and the check named it with those numbers.
- **C11.4** **0 is a count.** `.chips` was rendered unconditionally by `SearchPage`, so with no filters on there was an empty 12px row above the results, and applying the first filter shoved them down by the height of a chip. Fixed at the container rather than the call site — `.chips:empty, .rail:empty, .grid:empty { display: none; }` — so it is true of every instance, including ones nobody has written yet. `:empty` matches no children *and* no text, so a collection holding one chip is untouched. This is not an empty *state*: `.empty` is a component somebody renders on purpose.
- **C11.5** **A container that scrolls an axis is exempt on that axis.** Content past the edge is what a rail is for. Flagging it taught the content check to report two false breaks before this was added.
- **C11.6** Running past the edge is **reported, never failed**. Whether `.chips` at 8 filters (215px past, up from 151px since the chip took its 16px padding — C14.2) and `.rail` at 8 tiles (732px past) need an affordance is a design decision — both set `scrollbar-width: none` deliberately — and the report exists so somebody decides it rather than nobody seeing it.

## C10 — A control that says it is one line is one line

- **C10.1** `white-space: nowrap` is the stylesheet saying this control is a single line. One line has a height computable from the control's own box — line-height, padding, border, `min-height` — and anything taller means something inside took a line of its own. That is the filter-chip bug exactly: 32px became 48px when the close cross, being `display: block`, claimed a row.
- **C10.2** **The first version of this check was relative and proved nothing.** It compared a long-content cell to the control's rest cell and asked whether it grew. With the production bug reinstated it reported *nothing wrong*, because rest holds the cross too — both cells grew by the same 16px and the delta was zero. The invariant has to be absolute.
- **C10.3** It runs on every cell, not only the content ones. A control that is the wrong height with a short label is already broken; it has only not met a long label yet. With the bug reinstated this reports 6 breaks across rest, hover, focus-visible and both content cases.
- **C10.4** Also measured, and needing no baseline: a child whose box leaves its parent's, and content clipped with no `text-overflow: ellipsis` to say the end was lost.
- **C10.5** Growth is a defect **only** where the control declared itself one line. A toast is supposed to wrap — a message that cannot wrap is a message that gets cut off. Flagging it would have trained everyone to ignore the check.

## C14 — A control is at least 44px, and a pill stays wider than it is tall

- **C14.1** **44px is the floor, and the chip was the only control under it.** `.btn`, `.circ` and `.seg` all take `--control-h` (44px); `.sw` takes `--control-sm` (36px); `.chip` took its height from its text and came out **32px**. It is also the densest control the product has — a filter row is nothing but chips — so it is the one most often aimed at with a thumb. It is `min-height: var(--control-h)` now. `.sw` at 36px is still under the floor and is a separate decision.
- **C14.2** **Raising a `min-height` breaks the short end of the content axis, and that is a new failure, not a cosmetic one.** A pill is only a pill while it is wider than it is tall; below that it draws as a circle or a vertical ellipse, a shape the design never asks for. Measured at 390px with the real stylesheet: at 44px tall with the old 12px padding, `IN` came out **36.4 x 44** and `All` **38.7 x 44** — both taller than wide. The padding went 12px -> 16px in the same change, which puts `IN` at 44.4 x 44. **16px is the minimum that answers it** — it clears 44 by 0.4px, the tightest real case there is, and 14px would still leave it 40.4px wide. The cost is width: the eight-genre filter row runs 215px past its edge instead of 151px, and it already scrolls on purpose (C11.6).
- **C14.3** **Checked, not remembered.** `gallery:audit` now measures it: a control whose four computed corner radii each reach half its height is a pill, and a pill narrower than it is tall is a finding that fails the run. A control that is genuinely round — `.circ`, an avatar, a skeleton dot — is square, so it passes on equality rather than needing an exception. Proved by putting the 12px padding back: it names `IN` and `All` with the same two numbers measured by hand, and exits 1.
- **C14.4** **`padding-block: 8px` stays on the chip although `min-height` now decides its height, and it is load-bearing for a *check*.** C10's one-line expectation is `max(line-height + padding + border, min-height)`. A second line always costs a full 16px line, so with 8px of padding a two-line chip measures 48px against a 44px expectation and fires; with 0 it would measure 44px and vanish inside the new floor. Proved by reinstating the real production bug (`.chip { display: inline-block }`): still caught, 48px against 44px, audit exits 1. The margin is thinner than it was — anything over 33.5px used to fire, now anything over 45.5px — but the smallest two-line chip that can exist is 48px, so the class is still covered.

## C15 — A typeface the design names is a typeface the product loads

- **C15.1** The design system named Archivo, IBM Plex Sans and IBM Plex Mono from the first extraction, and **the product loaded none of them** — no `@font-face`, no font package, nothing in `index.html`. Every visitor saw whatever their device supplied, and because `--f-d` fell back to `sans-serif` while `--f-s` fell back to `system-ui`, the display and body type differed *by accident of fallback* rather than by design.
- **C15.2** **It survived because a missing face fails silently.** The browser drops to the next name in the stack and says nothing. Nothing in the product looked broken; it just was not the design. And every check in this repo was reading the same fallback and agreeing with itself — the gallery, the audit and `snap` all measured a face the design never asked for. **Loading the faces moved all 72 structural fingerprints**, with element counts unchanged on every one: the whole product's type had been wrong, and nothing had said so.
- **C15.3** Held by `verify` check 24: the **first** family in every stack must be one that an imported stylesheet actually declares a face for. First position only — the names behind it are fallbacks, and a fallback is allowed to be absent, that being its job. Proved twice: strip the imports and all three stacks fail, which is the original bug exactly; keep the imports but write `'IBM Plex Sans'` where the package declares `'IBM Plex Sans Variable'` and only that stack fails, which is the subtle version a reader would not catch.
- **C15.4** **Self-hosted, not fetched from a font host.** No visitor's IP goes to a third party, the files are fingerprinted on our own origin — and, decisively, **every check here runs in headless Chromium, often with no network.** A `<link>` to a font host would fail there and the harnesses would go on silently measuring the fallback, which is the very blindness being fixed. Variable faces where the family has one, so a weight can never be missing; IBM Plex Mono has no variable cut, so its four used weights are named. Mono needs no italic — the product's only two italic rules, `.tagline` and `.pbio.ph`, inherit `--f-s` from `body`.
- **C15.5** **The real face changes the numbers, so decisions made in the fallback have to be re-measured.** The eight-genre filter row went from 215px past its edge to 181px — Plex Sans is narrower than the fallback for mixed-case genre names — while `IN`, the tightest pill in C14.2, went the other way, 44.4px wide to 45.5px. The 16px padding holds either way, but it is now measured in the face that ships.
- **C15.6** Not covered: the gallery inlines Latin and latin-ext only, so a specimen in another script is measured in a fallback face, and non-Latin product text renders in one too. See CLAUDE.md §7.

## C9 — A glyph alone in a control is centred, and that is measured

- **C9.1** A control whose entire content is one glyph is making a promise that the glyph is in the middle. `gallery:audit` measures it in a real browser: glyph rect against control rect, both axes, every state, both themes. Over half a pixel is a finding.
- **C9.2** **It fails the run.** The rest of that audit reports — which states a stylesheet never answered is a design decision — but a crooked glyph has no defence, so this one exits non-zero.
- **C9.3** It checks the outcome, not the cause. The cause this time was the UA's `padding: 1px 6px` on `<button>`, never reset anywhere in the product, which leaves a `width: 24px` control with a 12px content box. The padding is symmetric, so it only breaks when the glyph is wider than `width - 12px` and overflow resolves to the start edge: eight of the nine affected controls were drawn correctly and were one icon-size change from not being. A check written against *that* cause would have passed on all nine.
- **C9.4** The reset is `button { padding: 0 }` in `shell.css`, beside the `font-family` reset that was already there. A button that wants padding declares it; a class declaration beats an element one.

## C16 — A geometric relationship is a relationship, not a number someone measured once

- **C16.1** **A negative margin is almost always one box pulled across another box's edge, and the distance is a constant somebody wrote down.** `docs/profile-module.html` §02 says the expanded avatar is *"96px, overlaps by 48"*. Nothing held the code to that: it shipped at 32 (taking `D1`'s literal `margin-top: -48px` against a row with 16px of top padding), and when that was corrected to 48 the value turned out not to be a constant at all.
- **C16.2** **`align-items: center` makes an overlap a function of the text beside it.** Under `center` a flex item's *margin box* is centred in the line, and the line is as tall as its tallest sibling — so the avatar's position was decided by how much the user had written about themselves. Measured at 1280, same markup, only the bio changed: **44px empty, 24px at four lines, 14px at `BIO_MAX`.** Under `flex-start` it is 48px at all four. A 30px swing driven by profile content, and it read as "4px out" because every measurement of it used the same one-line seed.
- **C16.3** **The failure is invisible by construction.** A sliding value measured once looks exactly like a constant. Three bugs in this repo survived review because everyone reasoned about the CSS instead of measuring the box (§6.2); this is the next layer — measuring the box is not enough if the box is only ever measured in one state. Twice in one day a *correct* measurement was taken against the wrong fixture: this, and a rail density of "7–13% occupied" read off a shelf holding one film where `PREVIEW = 8` means the ninth tile it described cannot exist.
- **C16.4** **Held in two halves, and both are needed.** `verify` check 26 requires every negative margin in the product to appear in `scripts/fixtures-registry.js` — as a relationship that is measured, or as a waiver saying why there is nothing to measure — so a new overlap cannot be *written* without the gate knowing about it. `npm run fixtures` then renders each declared relationship under several fixtures and fails when it **SLIDES** (the value moves), is **WRONG** (stable, but not what the design states), hits **NO SUCH BOX** (a selector matched nothing — absent is not passing), or is **VACUOUS**.
- **C16.5** **`VACUOUS` is the one that makes it a gate rather than a ritual.** Each relationship names the box its fixtures are meant to resize, and the pass refuses to report a pass until it has watched that box change — in width, height or child count, the last because a count fixture changes the DOM without changing the container. This repo has already shipped a check that compared a long label against a short one and measured a difference of zero because both were broken (§6.3); a fixture axis that moves nothing is that same check wearing different clothes. It fired twice on its first run, both times correctly: a 40-character name does not wrap at 1280, and a block-level flex container is the same width holding two faces or three.
- **C16.6** **Proved by reinstating the bug, five ways.** `align-items: center` put back → **SLIDES**, 48 → 44 → 14, exit 1, and it named the expanded band only while reporting the compact one as holding. A selector renamed → **NO SUCH BOX**. A stress box the fixtures cannot move → **VACUOUS**. A registry that said 64 where `--head-lift` steps to 80 → **WRONG**, which fired on its own, unplanned, on the first run. The stylesheet walker blinded → the C7.7 fail-open guard. Check 26 proved four ways in turn: a new undeclared margin, a waiver gone stale, a class that left the JSX, and its own walker blinded.
- **C16.7** **Not covered: nesting.** The pass renders the real stylesheets but writes its own markup, because nothing can render real JSX with a layout engine in CI. If `Identity.jsx` stopped nesting `.pav` inside `.pav-row`, every relationship would keep passing while the product broke. Check 26 closes the rename half — a class that leaves the JSX fails it — and the nesting half is open.
