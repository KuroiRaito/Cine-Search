# Cine Search — architecture audit

**Date:** 2026-09-13, after Milestone 3 merged (`main` at `d942ab0`).
**Purpose:** decide whether the codebase can support working on **one module at a time** — the detail page, the profile, the library — improving each to its best UI and UX without touching the others. Then say exactly what to do about it, in pieces another agent can pick up cold.
**Method:** every file in `src/`, `api/`, `scripts/`, `eval/` and `supabase/` read; the import graph computed; the live database inspected; the previous audit (`docs/archive/Architecture audit.md`, pre-rebuild) re-read against what exists now.

Read-only. Nothing in the codebase was changed for this document.

---

## 1. Verdict

**The code is small, well-layered, and organised the wrong way round for what you want.**

- **~4,300 lines** of application JavaScript, **1,156 lines** of live CSS. A restructure is a day's work, not a month's. That is the single most important fact in this audit.
- The data layers are genuinely good: TMDB transport → endpoints → normalise → view models is clean and documented; the Supabase write surface is four `SECURITY DEFINER` functions and nothing else; aggregation happens in one SQL function. **Keep all of it.**
- But the folders are organised by **technical layer** (`routes/`, `components/`, `hooks/`, `lib/`, `styles/`), not by **module**. "Work on the detail page" today means editing `routes/Title.jsx` (507 lines, four sub-components inline), `lib/tmdb/view.js`, `lib/library.js`, `components/ui.jsx`, and a 1,073-line `base.css` that also holds the library, taste, cover and settings styles. Nothing is pluggable because nothing has an edge.
- **Three things actually block modular work**, in order: one stylesheet for everything; the shared `Tile` primitive being wired into the library context; and the detail page being one file. All three are mechanical to fix.
- **686 lines are dead** (verified by the import graph, not guessed), the favicon is still Vite's, and native-app scaffolding is installed for a platform that was explicitly scheduled last.
- **Search regressed in Milestone 1 and nobody caught it**: filters and pagination were removed in the rebuild and never restored, despite AC 1.3.1 promising "no changes". It is the weakest module and the one your original brief cared about most.

**Readiness for per-module UX work today: not ready. After work packages 0–2 below (roughly three PRs): ready.**

**Data flow for one screen (Title):** `useAsync` → `endpoints.titleFull` (one TMDB call with seven `append_to_response`s) → `view.toTitleView` → JSX. Library state comes from `LibraryProvider` via `entryFor(mediaType, id)`. Writes go `LibraryProvider.save` → `library.upsert` → `rpc('library_upsert')`. Every write is optimistic, rolled back on failure, and announced on failure.

## 3. What is strong — keep it, build on it

| Strength | Where | Why it matters for modular work |
|---|---|---|
| **Four-stage TMDB layer** with one transport | `lib/tmdb/*` | Any module can add an endpoint without touching another module. Injectable fetch means the eval harness never patches globals. |
| **Server-only API key**, shared core for dev and prod | `api/_tmdbCore.mjs`, `vite.config.js` | Dev cannot drift from prod. The key cannot reach a bundle. |
| **Catalogue is client-immutable** | `catalog_ensure` `ON CONFLICT DO NOTHING` | A module can never corrupt shared data, so modules can be trusted to write. |
| **Aggregation in Postgres** | `taste_summary()` | The You module is one round trip. Store minutes, aggregate in SQL, format at the edge — the rule generalises. |
| **Per-section fetch state** | `hooks/useAsync.js` | "Errors scoped to the section that failed" falls out for free. A module's failure cannot blank another module. |
| **Optimistic writes with rollback and a spoken failure** | `LibraryProvider.commit` | Every module that writes gets the same guarantees without re-implementing them. |
| **One in-memory library, one source of truth** | `LibraryProvider.entries` | A title never shows two states in two modules. |
| **Design contract enforced in CI** | `scripts/verify.mjs` | Drift is a build failure, not a code-review opinion. This is rare and worth extending (§8). |
| **Tokens extracted, never hand-typed** | `styles/tokens.css` | The design artifact is the source; the file is a build product. |
| **Decision records, not just docs** | `docs/DATA_MODEL.md`, `GROOMING*.md`, `AC_*.md` | The *why* survives. A new agent can find out why a column exists. |

The previous audit's three urgent findings — `localStorage` auth, the unbounded proxy cache, and prop-drilling from a God component — are all resolved. Its recommendations to add Zustand and React Query are **not** taken up and should not be: two contexts and `useAsync` are sufficient for one user, and both libraries would add a layer between modules and their data for no benefit at this scale.

## 4. What blocks "one module at a time" — ranked

### 4.1 One stylesheet holds every module — **the blocker**

`base.css` is 1,073 lines in 25 sections. Editing the detail page's CSS means opening the file that also defines the library rows, the taste cards, the cover mosaic and the settings toggles. Two consequences already happened this session:

- A specificity collision between `.scores .s span` (title page) and a utility class rendered a label on two lines. Fixed by hand; nothing prevents the next one.
- The tablet band had to be written as a cross-cutting media query touching seven modules at once, because there was nowhere else to put it.

There is no mechanical way to know which classes belong to which screen. `verify` checks that every class has a rule; it cannot check that the title page isn't quietly depending on a rule written for the library.

### 4.2 The `Tile` primitive is wired into the library context

`components/ui.jsx` — the file of supposedly generic primitives — imports `useAuth` and `useLibrary`, because `Tile` reads the saved state to draw the ◷ / ✓ badge. Consequence: the poster tile cannot be rendered, designed or tested outside the providers, and every screen that draws a tile is coupled to the library module whether it wants to be or not.

The fix is small: `Tile` takes `state` as a prop; the library module supplies a `useTileState(item)` hook or a `LibraryTile` wrapper. The primitive becomes pure.

### 4.3 The detail page is one 507-line file

`routes/Title.jsx` holds the hero, the head, the action row, providers, scores, overview, `PreviewCard` (component), the four cards' content, `Episodes` (component with its own fetch, its own sign-in gating, its own runtime-capture effect), the related rail, the sign-in sheet and the editor mount. Two internal components and two large JSX constants. It works, but "improve the episodes experience" means scrolling past everything else, and the episodes section cannot be reused or previewed alone.

### 4.4 Shared files mix concerns

- `lib/library.js` (276 lines) is four things: the status vocabulary (domain), the RPC calls (infrastructure), the episode/progress maths (domain logic), and `formatDays`/`formatSpan` (presentation). Split along those lines it becomes `library/statuses.js`, `library/api.js`, `library/progress.js`, `you/format.js`.
- `lib/tmdb/view.js` (435 lines) is the view-model layer for three different screens plus the catalogue payload builder plus the person-credit relevance policy. It is the shared dependency of every module; it should stay shared, but the credit policy (`RELEVANCE_VOTES`, `isSelf`, `notableCredits`, `ROLES`) is person-module domain logic living in a shared file.

### 4.5 Twenty-five inline styles

`style={{ marginTop: 16 }}` and friends appear 25 times across routes and components. Each is a number outside the design contract that `verify` cannot see. They are small and each has an obvious class; they belong in the module's CSS.

### 4.6 The Discover head duplicates the shell

`Discover.jsx` renders search / theme / sign-in controls in `.head-actions`; the shell's top bar renders the same three. CSS hides one set at desktop. Two sources for one set of controls is a maintenance trap the moment either changes.

## 6. Found during the audit: regressions and unbuilt criteria

These are not opinions about quality. They are lines in accepted AC documents that the code does not satisfy.

### 6.1 Search lost its filters and its pagination — Milestone 1

`AC_MILESTONE_1.md` §1.3:

- **1.3.1** "Search behaves exactly as it does today. No changes to ranking, filters or pagination." — The M1 rebuild deleted `Filters.jsx` and the paginated results view. `SearchPage.jsx` has **no filters and no page 2**. `search()` is called with page 1 and the result is sliced to 20.
- **1.3.4** "Filters expand in place and push results down." — No filters exist.
- **1.3.6** "No results shows a spelling suggestion, the count of active filters, and a way to clear them." — The empty state says "Check the spelling"; there is no suggestion, no filter count, no clear.

The whole `lib/search/` layer — the variant seam, the eval harness, the golden query set, twelve committed runs — was built for a search experience that the results page no longer exposes. The infrastructure is intact; the screen on top of it is a fraction of what shipped before.

### 6.2 The title page fetches data it never shows

`endpoints.titleFull` appends `videos`, `external_ids`, `release_dates`, `similar` and `recommendations`. Of these:

- **`videos`** — trailers. Fetched on every title page, referenced nowhere in `view.js` or `Title.jsx`.
- **`external_ids`** — IMDb, Wikidata, Instagram ids. Fetched, unused. An IMDb link is the single most-requested thing on any film page.
- `similar` — used only as a fallback when `recommendations` is empty.

This is not waste to trim; it is finished data waiting for a UI.

### 6.3 Smaller

- `.head-actions` duplication (§4.6).
- The person page renders every filmography tile at once — 131 for Hans Zimmer — with no windowing. Fine today; the first time someone opens a prolific character actor it will not be.
- `useRegion` calls `ipapi.co` from the browser on first visit — a third-party request with the user's IP, unmentioned anywhere. It works; it should be a stated decision.

## 8. Target structure

Feature-first. Each module is a folder that owns its screens, its components, its CSS, and its domain logic. The foundation is the only thing modules import from outside themselves, besides each other's public exports.

```
src/
  app/
    App.jsx  main.jsx  Shell.jsx  routes.jsx        ← route table lazy-imports each module
    shell.css                                        ← shell, page furniture, states, breakpoints
  modules/
    entry/      Cover.jsx  Auth.jsx  SignInPrompt.jsx  entry.css
    discover/   Discover.jsx  discover.css
    search/     SearchPage.jsx  PeopleResults.jsx  Filters.jsx  search.css
                lib/  (index, v1, v2, types — moved from lib/search/)
    title/      Title.jsx  TitleHero.jsx  TitleActions.jsx  PreviewCards.jsx  Episodes.jsx
                title.css
    person/     Person.jsx  CollectionBar.jsx  credits.js (policy: ROLES, notableCredits)
                person.css
    library/    Library.jsx  Editor.jsx  LibraryProvider.jsx
                statuses.js  api.js  progress.js  library.css
    you/        You.jsx  Settings.jsx  TasteCard.jsx  format.js  you.css
  shared/
    ui/         Poster.jsx  Tile.jsx  Rail.jsx  PersonRow.jsx  Skeleton.jsx  Empty.jsx
                ErrorBox.jsx  Toast.jsx  ui.css   (rails, tiles, card, prow, toast)
    hooks/      useAsync.js  useRegion.js
    tmdb/       client.js  endpoints.js  normalize.js  view.js
    auth/       AuthProvider.jsx  supabaseClient.js
    theme/      tokens.css  theme.js  ThemeToggle.jsx
```

### 8.1 The CSS decision — the one that matters

Three options were weighed:

| Option | Scoping | Cost |
|---|---|---|
| Per-module plain CSS files, global class names | file-level only; collisions still possible | none — class names stay the design system's own |
| CSS Modules (`title.module.css`) | true | every `className="tgrid"` becomes `className={s.tgrid}`; the design HTML ↔ code correspondence that `verify` enforces breaks |
| Prefix every class (`.title-hero`) | convention | renames the design system's vocabulary; same break |

**Recommendation: per-module plain CSS, global names kept, and a new `verify` check that enforces ownership.** A class defined in `modules/title/title.css` may be used only by files under `modules/title/` (and `shared/`). Any other use fails CI with the file and line. That keeps the class names as the design system wrote them — which is the whole point of `verify` — while making leakage mechanical rather than a matter of discipline.

Vite concatenates the module stylesheets in import order, so cascade behaviour is unchanged. Breakpoints stay in `shell.css`; a module that needs a tablet rule writes it in its own file under its own `@media`.

### 8.2 The `Tile` decoupling

```jsx
// shared/ui/Tile.jsx — pure. Knows nothing about libraries.
export function Tile({ item, state, onAdd })          // state: { tone, icon, label } | null

// modules/library/useTileState.js — the only place that knows.
export function useTileState(item) → state | null    // reads LibraryProvider

// any screen:
<Tile item={it} state={useTileState(it)} onAdd={...} />
```

Same rendering, same badges, one import moved. `ui.jsx` stops importing any context.

### 8.3 Route-level code splitting

Once modules are folders, `routes.jsx` can `lazy(() => import('../modules/title/Title.jsx'))` per module. The 502 KB single chunk Vite warns about on every build splits into one chunk per module for free, and a module's bundle size becomes something you can see.

## 9. Scalability — what is fine, what is not, what not to do

The product is private, single-user, and not being rolled out. "Scalable" here means: will it keep working as *one* library grows, and will the code keep being pleasant to change.

| Concern | Today | Verdict |
|---|---|---|
| Whole library in memory | `loadAll` selects 13 narrow columns per row | Fine to several thousand titles. Revisit only if it ever isn't. |
| Person page renders all tiles | 131 for Zimmer, no windowing | Fine to ~300. Windowing is a one-component change inside the Person module when needed. |
| `taste_summary` | one query, O(library × genres) | Fine indefinitely at this scale. |
| Proxy cache | in-memory per instance, 60 s, 500 entries; edge `s-maxage=60` | Fine. No rate limiting — with no users, moot; note it if that ever changes. |
| Bundle | 502 KB, one chunk | Tolerable; §8.3 fixes it as a side effect. |
| Client-side query cache | none; `useAsync` + browser + edge cache | **Do not add React Query.** For one user it adds a layer between every module and its data for no measurable benefit. |
| Global state | two contexts | **Do not add Zustand.** Nothing is drilled; nothing is contended. |
| Tests | `verify` (static) + `smoke-api` | The gap that matters for UX work is **visual**: nothing checks what a module looks like. See WP-3. |
| TMDB availability | 5 retries, capped backoff, per-attempt timeout | Earned its place four times this week. Your ISP DNS-blocked `themoviedb.org` for two hours today; production was unaffected because Vercel resolves it from its own network. |

## 10. Work packages — for whichever agent picks them up

Each package is one PR. Each is self-contained: the agent needs this document and the repo, nothing from this conversation. **Order matters for WP-0 → WP-2; after that, modules are independent.**

Rules that apply to every package:

- **Move, don't rewrite.** Zero behaviour change in WP-1 and WP-2. If a screenshot before and after differs, the package is wrong.
- `npm run verify` and `npm run build` pass before the PR opens.
- The PR description says which module it touches and confirms it touched no other.
- Cut every branch from `main`. Do not reuse a branch after it is squash-merged (three phantom conflicts this week came from that).

### WP-0 — Housekeeping *(half a day, no risk)*

Delete: `src/App.css`, `src/index.css`, `src/hooks/useGenres.js`, `src/hooks/useMovieSearch.js`, `src/lib/searchFlags.js`, `src/assets/react.svg`. **Verify:** `npm run verify && npm run build && npm run test:api && npm run eval -- --limit 3` all pass.

### WP-1 — Foundation *(one day)*

1. Split `components/ui.jsx` into one file per primitive under `src/shared/ui/`. Move `useAsync`, `useRegion`, `lib/tmdb/*`, `supabaseClient`, `AuthProvider`, `theme.js`, `ThemeToggle`, `tokens.css` under `src/shared/` as in §8.
2. Decouple `Tile` (§8.2). `shared/ui/*` must import no context.
3. Carve the shared sections out of `base.css` into `shared/ui/ui.css` (rails and tiles, card, prow, toast) and `app/shell.css` (shell, page furniture, states, tablet, desktop). `base.css` keeps only module sections until WP-2 empties it.
4. Add two `verify` checks: **no inline `style={{`** in `src/modules/**` or `src/shared/ui/**` (fix the 25 existing ones by adding classes to the owning module's CSS); and **class ownership** — a class first defined under `modules/<m>/` may only be used under `modules/<m>/` or `shared/`.
**Verify:** all existing checks plus the two new ones pass; every screen screenshots identically at 390 / 900 / 1280 in both themes.

### WP-2 — Module moves *(one PR per module, half a day each, any order after Title)*

For each module in §7: create `src/modules/<name>/`, move its files, carve its `base.css` sections into `<name>.css` imported by the module's entry file, update imports, add the lazy route in `app/routes.jsx`. When `base.css` is empty, delete it.

Do **Title first** — it is your first UX target and the largest. Its move also splits `Title.jsx` into the five files in §8 (hero, actions, preview cards, episodes, page). Splitting is allowed here because it is pure extraction with no logic change; a diff reviewer should see only moved lines.

**Person** also moves the credit policy (`RELEVANCE_VOTES`, `isSelf`, `notableCredits`, `ROLES`, `roleForJob`) out of `shared/tmdb/view.js` into `modules/person/credits.js`; `search` and `you` import it from there.

**Library** splits `lib/library.js` into `statuses.js`, `api.js`, `progress.js`; `formatDays`/`formatSpan` go to `modules/you/format.js`.

### WP-3 — Visual check per module *(one day; the "runtime checks in verify" item from earlier)*

Add a Playwright script (`scripts/snap.mjs`) that starts the dev server against the test account, visits one representative URL per module at 390 / 900 / 1280 in dark and light, and writes PNGs to `snapshots/<module>/`. Not pixel-diffed and not gating at first — the value is that a module's PR carries its own before/after images, and a reviewer sees the module and only the module. Gate it later if it earns it.

### After WP-3: the UX work you actually want to do

Each module now has a folder, a stylesheet, an AC section, a snapshot set, and a public surface. Working on one means opening one folder. The briefs in §11 are where to start in each.

## 11. Per-module briefs — where the UX headroom is, and what data is already there

These are starting points, not specifications. Each lists what the module has that it isn't using, and which of its accepted criteria are unmet.

### Title (detail page)

- **Trailers are already fetched.** `videos` arrives on every title page and is dropped. A "Watch trailer" affordance in the hero or the action row costs no request.
- **External ids are already fetched.** An IMDb link (and Wikidata, for the Hobbyist persona's trivia hunger) is one line.
- `release_dates` carries every country's certificate and release; only the region's certificate is used. The Details card could show "Released 14 Jul 2024 (IN)".
- The four preview cards are "always these four, always this order" by design rule — but Themes is thin when keywords are sparse, and there is no card for *your* history with the title (started, finished, rewatches, your notes). Your own record is the one thing no other film app can show.
- Episodes: "Jump to episode" was deliberately deferred; the season switcher scrolls horizontally with no indication of which seasons carry progress.

### Person

- **Collection bar is done; the filmography grid is not designed for 131 tiles.** Sorting (year / rating / seen-first), and a "seen" filter, are the obvious next controls — the design shows a "Year ▾" control that isn't built.
- The person's photo is the only image; TMDB `images` (appended already) has more.
- Known cost to state on the page: at 200 votes, Emilia Clarke shows 12 of ~20. "N credits filtered out" is honest; "why" is not yet explained anywhere a user can read.

### Library

- No search or sort inside the library (deferred at grooming; becomes real at ~50 titles).
- Changing status from a row was struck (AC 2.5.6). The row already shows the status; the design's own "long-press → editor" is the smallest possible addition if it is ever wanted.
- Series rows show progress; film tiles show nothing but the poster. Rating on the tile is data already in hand.

### You

- Person cards need a TMDB fetch per card for the denominator; a `catalog_people.credit_totals` cache (fill-when-absent, like season runtimes) would make the screen one round trip again. Only worth it if the fetches are felt.
- "Score" ordering has a floor of three rated titles; there is no way to see *why* a card isn't there. A muted "rate 2 more to rank" would close that.
- Rewatch semantics remain open from M2 grooming: do episode ticks clear per pass, or persist? `rewatch_count` is a manual stepper today, so nothing depends on it — but the You screen multiplies hours by it, so the question now has a visible consequence.

### Search — **the weakest module, and the one the original brief was for**

- Restore **filters** (All / Films / Series / People per the design; genre, year, rating per the old UI) and **pagination**. AC 1.3.1, 1.3.4, 1.3.6 are open.
- The **no-results** state should offer a real spelling suggestion — `search/v2` is the seam for typo tolerance, and the eval harness measures it. The golden set already contains "intersteller".
- The eval harness measures `search()`; nothing measures the *people* results. Add them to the golden set.
- Twelve baseline runs are committed under `eval/runs/`. No v2 run exists. The measured defects in `v1.js` (re-sorting by popularity, client-side filtering forcing deep pagination) are documented and unaddressed.

### Discover

- Four fixed rails. The design's "guest home" shows genre rails and a "because you watched" rail; the second is now buildable from `taste_summary` for a signed-in user.
- Remove the duplicated `.head-actions` (§4.6) once the shell owns those controls at every width.

### Entry

- Complete as designed. The only open item is yours: leaked-password protection in Supabase Auth.

### Shell

- The 700–1120 px tablet band was designed in code, not in the design system. It holds, but it is the one range the artifact does not show; a single tablet frame in the design would close that.

## 12. Summary for the owner

- **Strengths to keep:** the TMDB layers, the write surface, SQL aggregation, per-section fetch state, optimistic writes, the design contract in CI, the decision records.
- **Three blockers to modular work:** one stylesheet, a context-coupled `Tile`, a monolithic `Title.jsx`. All mechanical. WP-0 → WP-2 is roughly three focused days.
- **One regression to own:** search lost its filters and pagination in M1. It is also where the most infrastructure is waiting for a screen.
- **Two things not to do:** React Query, Zustand.
- **The order:** WP-0, WP-1, WP-2 (Title first), WP-3. Then the module briefs, one at a time, in whatever order you like — that is the point.
