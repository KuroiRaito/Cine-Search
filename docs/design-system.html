The complete system: three twelve-step colour scales, a six-state watch palette, the control set, all nine MVP screens, and a live section rendered with real TMDB data. Every screen is the same handful of components recombined — which is the point of having a system at all.

All business rules here are mine. Reasoned from the personas, the data inventory and the benchmark — not from a PRD, because there isn't one yet. They're numbered R1…R26 so you can reject one by number. Sample data is illustrative; where I've assumed a field exists, the rules say so.

Colour scales

Three scales, twelve steps each, every step with one job. Semantic tokens alias steps, not hex values — so switching theme swaps which scale is active rather than re-tuning colours by hand. The dark theme is unchanged from what you shipped: ink-1 is #0A0F1B, beam-9 is #25BADF, marquee-9 is #F5C45C.

Rules

Rules
  1. Errors are scoped to the section that failed, never the whole page. A dead provider call must not blank a title page that already has its synopsis.
  2. Every empty state names one action. Never a bare illustration.
  3. No-results always offers a spelling suggestion and a filter escape, with the active filter count shown — the most common cause of zero results is a filter the user forgot.
  4. Skeletons mirror the layout that's coming, so nothing shifts on arrival.
  5. Any named person is a person row, never loose text. Photo, name, role, chevron — the same component whether it's a creator, a director or a cast member, so every name on every screen behaves identically and lands on the same page shape.
  6. Missing photo degrades to initials, and the row stays tappable — a person page is still worth opening without a headshot.
  7. No person record at all → initials, no chevron, not tappable. The name is still shown, because the credit is true even when we can't navigate to it. A link that goes nowhere is worse than plain text.

Entry & guest

Three screens the eight didn't cover, all following from §12's decision that guests browse freely and sign up to save. The governing constraint is §1: "feel natural, like home — never forced." A hard login wall is the most forced thing an app can do, so none of these gate the catalogue.

1 · Cover

First visit only. Skippable, and it doesn't come back.

Cine Search

Rules
  1. Shown once, on first visit only. Set a flag locally and never show it again — returning guests go straight to Discover. A cover page that reappears every visit is a wall, and §1 forbids walls.
  2. "Browse without an account" is a real, visible action — not grey 11px text in a corner. The Noob's entire persona is browsing before committing; burying the skip loses them at the door.
  3. Create account is primary, Sign in is secondary. Most people hitting this screen are new. A returning user recognises "Sign in" regardless of its weight.
  4. The mosaic is real artwork, never stock illustration. The catalogue is the product; showing it is the most honest possible pitch.
  5. Attribution lives here too. TMDB and JustWatch credit is contractual, and this is the first screen — cheapest possible place to satisfy it.

The one decision worth your attention is the cover page's recurrence. I've specified first-visit-only, which respects §1 but means a returning guest never sees the pitch again. The alternative — showing it every signed-out visit — converts better and feels more like a wall. Given that the stated failure condition is "it gets harder for any persona", I'd hold the line on once-only, but it's a growth decision as much as a design one, and it's genuinely arguable.

Build contract · how shape drifts, and how to stop it

Auditing the running build surfaced a pattern worth naming: the screens were right, but individual components came out a different shape from the design. Not because anyone disagreed — because the design said what things should look like and never said what they must measure. These rules close that gap. They are deliberately mechanical: a developer agent should be able to verify each one without judgement.

The failure that produced both reported problems

A class name in the markup that has no box rule in the CSS fails silently. Discover.jsx renders <div className="card signup">, but .card is never defined — only .card.signup{text-align:center} and some font sizes. So the element gets no background, no padding, no radius, no margin. Measured at 375px: box left:0 right:375, text starting at x = 0, flush against the screen edge, and margin-top:0 butting the rail above with zero separation — while every poster tile beside it is inset to left:14px. There is no geometric overlap, but it reads as one, because the block breaks the page's rhythm in both axes at once.

Rule zero

  1. Every class in the markup must resolve to a rule that sets box properties. A class that only sets typography on top of a base that doesn't exist is the single most common way a component silently loses its shape. If .card is referenced, .card must define background, padding, radius and margin — before any modifier tunes it.
  2. One gutter token, obeyed by everything. --gutter: 14px at mobile, 24px from 700px, 40px from 1100px. Every top-level block's content starts at exactly the gutter. Nothing gets its own number.
  3. Full-bleed is opt-in and explicit. Only backdrops, hero images and horizontally-scrolling rails may touch the viewport edge, and they need a .bleed class to say so. Even then, their text and controls stay gutter-inset. A rail's posters may run off the edge; a rail's title never does.
  4. Vertical rhythm is never zero. Consecutive top-level blocks are separated by at least --s6 (24px). Two blocks sharing an edge is always a bug, never a layout.
  5. Build the base component before the instance. No .card.signup without .card; no .sheet-title without .sheet. Modifiers tune, they never constitute.

Verification checklist

Mechanical, and all of it checkable in the browser console at 375px:

  1. Every top-level block's content left edge equals the gutter. [...document.querySelectorAll('main > *')].map(e => e.getBoundingClientRect().left) — every value is the gutter, or the element carries .bleed.
  2. No block has a zero gap with its neighbour. Compare each block's bottom with the next block's top; the difference is never 0.
  3. No text sits within the gutter. No text node's bounding box starts left of the gutter, on any screen.
  4. Every referenced class exists. For each className token in the JSX, a matching rule sets at least one of background / padding / margin / border-radius.
  5. Nothing overflows horizontally. document.documentElement.scrollWidth === innerWidth at 320, 360, 390 and 430.
  6. Both themes resolve. Toggle theme and confirm no element keeps a literal hex — every colour traces to a token.
Why mechanical rules and not principles. "Cards should be inset and separated" is something everyone agrees with and nobody can check. "Every top-level block's left edge equals the gutter, and no two blocks share an edge" is something a build step can fail on. The drift you found came from the design describing appearance without specifying measurement — so these rules give measurements, and the checklist gives a way to prove them.

Guest state · implementation spec

Audited against the running build on 2026-09-12, route by route, at 375px. The new routes follow the design closely. What follows is the explicit per-screen contract, plus the four defects the audit found — all of which sit in components the guest journey passes through rather than in the guest routes themselves.

Explicit rules

  1. No route ever redirects a guest to sign-in. Only actions prompt. Reading is always free; writing is what needs an account. A redirect punishes someone for arriving.
  2. Every tracking affordance stays visible to guests — the +, the status pill, the heart, episode ticks. Hiding them hides the product from the people who haven't bought into it yet. They are not disabled, not greyed, not aria-disabled: they look live, because tapping them does something.
  3. The prompt names the title and the action, and the intent resumes after authentication — the user lands back where they were with the action completed. This is the single most important rule here: if someone signs up to save a title and it isn't saved, the first promise the product made was broken.
  4. The person page shows the filmography, not a zeroed meter. A guest must never see 0 of 10 directed — a real number that happens to be a lie about them. Replace the meter with one quiet line: "Sign in to track what you've seen". Everything else on the page is identical.
  5. Empty states explain the account, they don't sell it. One sentence on what an account stores, one button. No feature lists, no second CTA, no repeated card per section.
  6. A guest is someone who isn't signed in — never a fabricated user object. No guest-local-id, no mirrored localStorage library. §12 called that "a standing tax": two databases to maintain forever the moment episode progress and rewatch counts land. The current build gets this right and it should stay that way.
  7. Sign-in entry points: exactly three, each with a different job. Top bar (navigation), the one Discover card (conversion), and the action prompts (intent). Anything beyond that is nagging.

Cases that only exist on desktop

The screens above are layout. These are the genuinely new problems — the ones a mobile-only design never has to answer.

CaseDecision
Hover existsThe tile + stays always visible, not hover-revealed. Hidden-until-hover is undiscoverable, breaks on touch laptops, and the button is small enough that showing it costs nothing. Hover changes its colour, not its existence.
Keyboard navigationSegmented controls are arrow-key navigable as a single tab stop, not six. Esc closes the editor; ⌘/Ctrl+Enter saves. Every focusable element keeps the visible focus ring the system already defines.
Line lengthThe overview caps at ~65 characters even in a 1120px column. Full-width body text is the most common desktop failure and the easiest to avoid.
Very wide screensPage content caps at 1280px and centres. Rails may extend to the viewport edge; reading columns never do.
Sticky rail shorter than contentThe action rail sticks to the top of the viewport. If the rail is taller than the viewport it scrolls normally and stops sticking — never traps its own content out of reach.
Nav has nowhere to goBottom tabs become a top bar. The fourth destination ("You") moves into the avatar menu, since profile and settings are a session concern rather than a browsing one.
Long episode listsA 62-episode season stays a single column at desktop. Two columns break the natural reading order of a numbered sequence, and the list is scanned rather than read.
The editorBottom sheet → centred modal, two-column form. Every field visible without scrolling, so Save moves from the header to a proper footer with an explicit Cancel.

Search, Taste and the state screens aren't drawn separately because they're the patterns already shown — Search is the Library grid with a query bar, Taste is the same taste cards at 3-up, and the state screens are unchanged apart from centring within the wider column.

The day-one cost is small; the retrofit cost is not. None of this needs designing now — it needs the components to not assume a 430px container. Fluid widths, a column count driven by a variant rather than hardcoded, a nav that can render as tabs or a bar, and the editor able to mount as either a sheet or a modal. Get that right while building m-web and desktop is a layout pass. Hardcode 430px and it's a rewrite.

Small screens · verified, not assumed

Everything above is drawn at 430px, which proves nothing about narrow phones. So this was tested rather than asserted: the page was served locally, rendered in a real browser at a 320px viewport, and every element inside every phone frame measured for horizontal overflow.

Rules

  1. 320px is the supported floor. src/index.css already sets body{min-width:320px}, so the app has effectively declared this. Keep it, and treat anything narrower as out of scope.
  2. white-space:nowrap is permitted only inside a horizontal scroll container. Chips and the season switcher qualify because they scroll. Content text never does — it wraps.
  3. Wrap, never truncate — except where clamping is deliberate. The only intentional truncation is line-clamp:2 on grid tile titles, and it is a design choice with a tooltip and a full title on the detail page behind it.
  4. Rows grow in height rather than squeezing. A long episode title takes three lines at 320px. That is correct; the alternative is an ellipsis that hides which episode it is.
  5. Secondary labels may shorten below 360px — TMDB · 8.5k becomes TMDB, Your score becomes You. Shorten the label, never the number.
  6. Thumbnails are fixed-width and that is fine, because they're small (40–82px) and everything beside them is fluid. Fixed widths are only dangerous on text containers.
  7. Test matrix: 320 / 360 / 390 / 430. 360 is the most common Android width and 390 the most common iPhone; neither is an edge case. This belongs in the acceptance criteria, not in a QA pass at the end.
The lesson worth keeping isn't about width. The only genuine defect this pass found was a missing charset — a bug that is invisible in the environment I was designing in and only appears in the environment the file is actually used in. Rendering it somewhere real found in one minute what reading it would never have found at all.
