Find

There is a golden set in this repository of 120 things people actually type. Run through the search that ships today, 62% of them come back with nothing at all — and the reason is not the ranking. It is that the box is wired to one engine when the question needs the other. Everything below was measured against live TMDB this week, including one hypothesis of mine that the data killed.

01

What people type, and what comes back

eval/queries.json holds 120 queries in nine categories, built for this product and graded by hand. It is the best research asset the repository has. It had 50 labels and a run covering 40 — and the unlabelled seventy were the six categories that fail, so nothing about them could be measured, only asserted. All 120 are now labelled and scored; the method and its two traps are in eval/LABELS.md.

So I ran all 120 through /search/multi, as they are typed, and then again through two normalisations. Zero-result rate is the column that matters: it is the share of queries that produce a screen with nothing on it.

02

Two engines, one box

TMDB does not have a search endpoint with filters. It has two separate engines that share nothing, and almost every problem in this module is a consequence of that one fact.

/search/multi — the name engine/discover/movie|tv — the filter engine
Answers“What is it called?”“What kind of thing?”
Free textYes — word-prefix, strict AND across every wordNone. At all.

L1 — a query and a facet never travel in the same request. There is no endpoint that takes both, so any screen offering “search and filter by genre” is promising something that has to be faked client-side. We know what that costs, because v1 did it: 84 TMDB calls and 9.6 seconds to build one filtered page five. The filter row is therefore not one row — it is two rows that swap, depending on whether the box has text in it.
FacetWith text in the boxWith the box emptyWhy
All / Films / Series / PeopleOfferedOfferedFree either way. On a query it is a client-side split of one response that already arrived, not a second request.
YearOfferedOffered (as a range)The one filter both engines support. Also how a pasted “Inception (2010)” is rescued — §04.
Genre, language, runtime, rating, provider, sortNot offeredOfferedThe name engine cannot do them, and faking them costs 84 calls. Picking one with text present converts the search into a browse, and says so.
This is the whole design, in one sentence. A person moves along a single axis — how much do I already know? — and the screen moves with them: rails when they know nothing, facets when they know a kind, a name when they know the thing. One module, three states of the same machine, and the box is the pivot between them.

03

One module, three variations

Discover and Search are two tabs in the app and two folders in the repository, and they are the same machine at two settings. Following the hierarchy the title module settled on — module → variation → cohort — Find has three variations, and the third one does not exist yet.

Find module — every screen that ends in “open this”
 ├─ Discover  FD   ├─ guest
 │                     ├─ new        signed in, nothing logged
 │                     └─ active     a library with something in it
 ├─ Query     FQ   ├─ named a title
 │                     ├─ named a person
 │                     ├─ named a franchise
 │                     ├─ described a kind      convertible to Browse
 │                     └─ named nothing we hold the rescue ladder
 └─ Browse    FB   ├─ results
                       ├─ too few    and the screen names the chip that did it
                       └─ too many   a sort is doing the work, not a filter
The same test as the title module. A cohort may change the primary answer, change what the answer means, and omit bands. Only a variation may add or reorder them. So named a person may put a person where the grid usually starts — that is changing the answer, not adding a band — but only Browse may introduce a sort control, because only Browse has an engine that can sort.

Four tabs stay four tabs

The obvious move, having found one machine, is one tab. I do not recommend it, for three reasons and one of them is the product's.

OptionVerdict
Merge into one Find tabNo. Discover is the app's front door and a tracker's front door should open onto your shelf, not a search field. Merging also costs a tab and buys nothing: Browse needs an address, not a tab.
Add a fifth Browse tabNo. Five tabs at 320px is 64px each. And browse is not a destination people go to cold — it is where a rail, a genre chip or a failed search sends them.
Keep four; Browse is a state of SearchYes. /search with facets and no query is Browse. It gets a URL, a back button and a share, and it is reached from every rail header, every genre chip on a title page, and every empty result.
One thing to delete on the way past. Discover.jsx draws its own search icon, theme toggle and sign-in button in .head-actions, duplicating three controls the shell's top bar already owns at desktop. The module's own notes flag it. With the search box reachable by tab and by rail, the page-level copy has no job left.
04

The rescue ladder

Five rungs, measured one at a time against the golden set. Each rung runs only when the one above it came back empty, so a query that works never touches any of them. What matters for the design is not the mechanism but what the screen says at each rung — because a search that quietly answers a different question is a search nobody trusts twice.

RungWhat it doesMeasuredWhat the screen says
0Ask as typed62% of the golden set returns nothingNothing. This is the happy path for 38%.
1Drop the words that are not part of a name — movies, films, show, series, all parts, in order, trilogy, with, by, best62% → 44%. Franchise 80→0, person-led 40→7, attribute 100→60. hit@5 unchangedNothing. The only silent rung, and it earns it: it removes words the index cannot hold and changes no result that already worked.
1bSplit a trailing year off the name and pass it as yearinception (2010) → 0 results today. Inception 2010 → 0.Nothing — the year becomes a chip, visible and removable. Pasting a title with its year is the most natural paste there is, and today it is a dead end.
2Strip Hindi particles and honorifics — ki, ka, ke, koi, bhai, ji, saab44% → 42%. salman bhai ki movie → Salman Khan, rank 1Nothing. Same argument as rung 1.
3Truncate to the longest prefix that still matches, never below six characters — and only if what remains does not parse as facets, in which case this rung is skipped and the answer is a browse9 of 18 typos, at rank 1 in eight of the nine. intersteller→interstell, pulp ficiton→pulp fic, game of thornes→game of thOut loud. “Showing results for interstellar”, with search instead for “intersteller” underneath it.

Did you mean Forrest Gump?” — because two of the four land at rank 2, behind a wrong answer.
5Edit distance against a dictionary of popular titlesThe only rung that reaches the last five: gladaitor, titanc, dangl, sholeySame as rung 4. The only rung with a cost — it needs a list we do not ship. Design says what the screen does; whether the list is worth it is a build call.
Six characters is not a round number, it is where the evidence stops. TMDB matches word prefixes, so truncation works — until the prefix stops being the word. titan returns 610 results and none of the first twenty is Titanic; it is Attack on Titan's, fairly. shol returns people called Sholto-Douglas. dang returns a film called Dang!. Below six characters a correction quietly becomes a different search, which is exactly the failure rung 3 exists to prevent.
A hypothesis of mine that the measurement killed. I expected that re-ranking the truncated results by popularity would rescue the short ones — Titanic is far more popular than anything else matching titan. It rescued nought of eight. The reason is simple once you look: Titanic is not in the twenty results being re-ranked, so no ordering of them can find it. Re-ranking cannot add a result. Recorded because the wrong version of this is a plausible thing to build.
L2 — the box never answers a different question silently. Rungs 1, 1b and 2 remove words that are not part of any name, so nothing is being reinterpreted. Rungs 3, 4 and 5 change the name itself, and every one of them must print what it did and offer the original back in one tap. The band is one line above the results — never a toast, which disappears, and never a dialog, which interrupts.

With all 120 labelled, the ladder stops being a proposal. I ran rungs 1–4 outside the app — same queries, same labels, same metric as §01 — against the shipped v2:

nDCG@10 goes 0.23 → 0.36, a 57% improvement, for four rungs of string handling and no new data.

Read the two columns against each other, because they disagree on purpose. The empty screen nearly disappears — 66% to 5% — while genuine usefulness moves only from 25% to 40%. The ladder converts empty screens into populated ones, and for four categories the population is wrong. That is not a disappointing result, it is the argument for the rest of the module stated in numbers: “christopher nolan movies” now returns twenty films and none of them is his, because his films are not in a name index — they are behind the person route (§08). “movies from the 90s” returns twenty films and none is from the nineties, because that is a browse (§02). A string can only ever be rescued into another string.
And the simulation found an ordering bug in my own ladder. Rung 3 answered 44 of the 120 — far more than it should, because truncation runs whenever rungs 1 and 2 come back empty, including for queries with no title in them at all. Truncating “movies from the 90s” to “movies from the 9” is not a correction, it is a different search that happens to return something. The fix is an order, not a new rung: after rung 2, check whether what remains parses as facets — a genre, a language, a decade, a runtime — and if it does, go to Browse and stop. Truncation is for a name somebody spelled wrong, and only for that.

When nothing survives the ladder

At 62% today and 42% after the free rungs, the empty screen is the most-visited screen in this module — more common than any single result. It is currently a heading, a sentence and a link to Discover.

The benchmark sets a low bar here, which is a gift. AniList — the app this product is measured against — answers attak on titan with the words “No Results”, centred, and nothing else. No correction, no suggestion, no route out. This is the one screen where being better is cheap.

So it carries four things, in this order, and each is absent when it has nothing to give:

05

Facets, sorts, and the floor that should not exist

The filter engine is the half of the product that has never been built, and it answers the categories the name engine cannot. Three of its properties will decide whether it feels right, and all three are counter-intuitive enough to be worth stating as laws.

L4 — a rating is a band, never a sort, and it is ordered by evidence

Sort by rating with no minimum vote count and TMDB is perfectly happy to hand back four films rated 10.0 from a single vote. The reflex is a floor — and the canon does appear, but not until the floor is high:

3,000The Shawshank Redemption, The Godfather — what a person means by “highest rated”

A fixed vote floor is an anglophone bias with a number on it. The floor that makes English sensible — 1,000 votes — leaves Telugu, Tamil and Malayalam with nothing at all and Hindi with three. A person in India sorting by rating would be shown, by a product built for them, that their cinema does not exist.

Two cleverer floors, both measured, both wrong

The first draft of this section said the floor should be derived from the language's own distribution rather than fixed. That sounds right and is not, and the only way to find out was to build it:

DerivationWhat it producesVerdict
Search for the floor that keeps ~100 filmsEnglish 5,000 votes → 96 films. Telugu 2 votes → 121 films. Tamil 2, Hindi 4, Korean 7.No. “Rated 8+ by two people” is noise with a rosette on it. Cheap to compute — twelve calls, cacheable — and worthless.
Keep the top 10% of that language by vote countA floor of 2–4 votes for every language, English included — because 20,001 English films are “rated 8+” once one-vote films count, so a tenth of them is 2,692.No. The tail is so long that any percentile of it lands in the noise. A percentile of a corpus that is mostly noise is noise.
So there is no floor. A rating is a band, and the band is ordered by how many people voted. vote_average.gte=8 with sort_by=vote_count.desc — nothing is excluded, and the films nobody has seen sit in the tail where they belong instead of being deleted from a catalogue. One rule, no table, no derivation, no language to apologise to. Verified, page one, six languages:

And the tile prints the vote count, wherever a rating is being sorted or filtered on. 8.0 from 79 votes and 8.5 from 41,165 are different claims and must not render identically. This is what makes the no-floor rule safe: the weak evidence is still visible as weak evidence rather than hidden by a threshold somebody chose on the reader's behalf. It is one number on a tile that already carries the score, and it is the whole defence.
What the failed derivations bought. Nothing in the first two rows of that table is wasted: they are the reason the answer is allowed to be this simple. Without them, “just sort by votes” reads as the lazy option rather than the one that survived.

L5 — genre is two vocabularies that happen to share eight words

Films have 19 genres, series have 16, and only eight exist in both — with, usefully, identical ids: Animation, Comedy, Crime, Documentary, Drama, Family, Mystery, Western. Action is film-only; series call it Action & Adventure. Science Fiction and Fantasy are two film genres and one series genre.

So the genre row is not one row either. With the medium set to All it offers the eight shared genres and nothing else — every one of them means the same thing on both sides. Choosing Films or Series unlocks that medium's full list. And switching medium with a medium-only genre selected drops the genre and says so in the chip row — silently mapping Thriller to Action & Adventure would be inventing an answer.

The clutter budget

At rest: one control. The box, and a filter button beside it. No facet row, no chips, nothing to read. Open: three rows and a switch — Kind, Genre, Language, and Hide what I've seen. Behind More: four more. Eight facets exist; three are ever visible without a deliberate tap. On desktop the first five sit in the row permanently, because a 1120px band has the space a 320px one does not — the set does not change, only how much of it is already unfolded.
L7 — a facet appears only when it can change the answer. No where to watch before a region is known. No genre the current medium does not have. No Series in a result set that is all films. A control that cannot do anything is worse than a missing one: it is a promise the screen breaks when you touch it.
L8 — no Apply. Every change applies immediately and the count above the grid is the feedback — 394 films becomes 41 films as the chip goes on. That single number is what the old modal could not show, and it is the difference between choosing a filter and guessing one. The panel stays open while you work; the results move underneath it.
Two places show state, and they have different jobs. The chip row above the results is the record — always visible, each chip removable, nothing hidden. The panel is the editor, and it is closed most of the time. The filter button carries the active count so a closed panel never conceals a constraint. This is the one duplication in the module and it is deliberate.

When the query names a person, or a franchise

The person rule, amended

The search module carries a written rule: people rank alongside titles, never above them — so the person section sits after the grid. It was the right call when it was written, and the measurement says it is wrong for one specific case.

Measured on the 15 person-led queries
Right person at TMDB's rank 1, after rung 113 of 15 — Nolan, Tarantino, Scorsese, Gerwig, Villeneuve, SRK, Aamir Khan, Rajkumar Hirani, Anurag Kashyap, Deepika Padukone, Nawazuddin Siddiqui, Brad Pitt, DiCaprio
The two failuresmovies with tom hanks and films by wes anderson — both fixed by adding with and by to rung 1, both then rank 1
What sits above them todayThe title grid — which for tarantino is Take Tarantino (2006) and Making Tarantino, and for shah rukh khan is Shah Rukh Khan Ki Maut
Amendment, not repeal. When the query names a person — TMDB returns them at rank 1, they pass the existing plausibility gate of a photo and a pulse, and no title matches the words strongly — the person row goes first, and the grid below it is their work. In every other case the rule stands: people after titles. The old rule protected against “dune” surfacing an actress called Aggy Dune; this exception does not weaken it, because dune has a title that matches the words strongly and tarantino does not.
And the row already knows the interesting thing. PersonRow carries “Director · 6 of 10 seen” — collection progress against their body of work. That number is the wedge this product has and the others do not, and promoting the row surfaces it one screen earlier. The row opens the person page, which the title module already designed as its third variation; the search does not build a second filmography.
The collision case is real and already documented. Two people can share a name — person/151 is Roger Deakins the cinematographer, person/4313 is Roger Deakins the makeup artist. When two plausible people match, neither is promoted: both appear as rows, each carrying the evidence line that tells them apart. State TP5 in the title module, FQ6 here.

The franchise rule, and a tempting endpoint that ranks badly

“harry potter in order”, “avengers all parts”, “lord of the rings trilogy” — ten of the golden set, 80% empty today, all of them zero after rung 1 strips the three words at the end. The obvious next step is /search/collection. I checked it, and it should not be the primary path:

Query/search/collection top hitTop film's belongs_to_collection
avengersAvengers Grimm CollectionThe Avengers Collection
lord of the ringsThe Making of The Lord of the Rings CollectionThe Lord of the Rings Collection
harry potterHarry Potter CollectionHarry Potter Collection
toy storyToy Story CollectionToy Story Collection
The franchise comes from the top film, not from a collection search. Collection search found something for all ten — and led with the wrong thing twice out of four checked, including a making-of documentary. The top film's own collection was right four times out of four. So: the grid answers as normal, and one band above it reports the collection the top result belongs to — in release order, with the number that matters: Harry Potter Collection · 8 films · 3 seen.
A note on how this was nearly reported backwards. My first pass at collection search recorded zeros for seven of ten queries and I almost wrote that the endpoint was useless. They were connection resets that my own probe was swallowing and reporting as “no results” — which is, precisely, the bug this module is about. A failed request and an empty answer look identical on screen and mean opposite things. The shipped people search already knows this and retries once; every request in this module inherits that rule, and a failure says could not reach TMDB, never nothing found. State FQ12.

Decisions, and what this hands over

Settled — groomed 18 September 2026

All seven closed in one pass. Five went the way the recommendation argued; none was overturned; the reasoning is kept so a future reader can see what the ruling cost.

IdQuestionRuling
FD-1Is the typo dictionary worth it? The four free rungs reach 13 of 18 typos; the last five need a shipped list of popular titles and edit distance over it.Not yet. Ship rungs 1–4, which cost string handling and no new data and take zero-result from 66% to 5%. Five of eighteen golden queries is a thin case for a data file somebody has to keep fresh. Revisit when there are real logs of what people actually mistype — that is a better list than any dictionary we could pick today.
FD-2Recent searches — stored where?On the device, and clearable. Local storage, last eight, a Clear in that list's header. It never leaves the device, so there is no table, no RPC, and nothing to explain in a privacy note. A search history is mildly sensitive and this is the version that stays that way.
FD-3Does Browse deserve its own route?No. /search with facets and no query is Browse. One route, one back-stack, one mental model — and the URL already tells them apart.
FD-4Should the presets be editable?Not in this pass. Ship the six and let the chip row teach people that a preset is only facets. If saved searches are ever wanted, that is the shape they take.
FD-5Language default for an Indian region.No pre-set filter, ever. A filter nobody chose produces results nobody can explain — the same failure as a vote floor nobody set. Closer to home sits in the presets instead: offered, not applied.
FD-6Should Hide what I've seen default to on?Off. One tap to turn on, remembered for the session once used. On by default would mean somebody searching for a film they logged is told it does not exist.
FD-7Multi-select genres?Single-select first. TMDB ANDs them and an AND of two genres is usually a handful of films. Ship one at a time, then watch for people swapping a genre off and another on within a second — that behaviour is the evidence that would change it.
Grooming is closed for this module. Nothing above blocks a build. Two follow-ups are watch-items rather than open questions: FD-1 reopens on real typo logs, and FD-7 reopens on rapid genre swapping. Both need usage that does not exist yet, and neither changes a line of what ships first.
One thing that is still genuinely open, and it is not a design decision. Nineteen of the golden set's labels are mood queries graded by judgement — mine. They are marked claude-judgement-2026-09-18 in eval/queries.json and each carries its reasoning. Every mood number in this document rests on them, so they are worth an hour of somebody else's eyes before anybody optimises against them.

Two things in the shipped code that this design assumes are fixed

The quick-add control is a typographic plus, not the icon. Tile.jsx renders {state ? state.icon : '+'} — a text character sitting beside 33 Lucide icons drawn on a 24px grid. It is the last survivor of the glyph set the icon pass removed, it appears on every tile in the product, and it is one import. Dev handoff.
One new icon role, and only one: filter → Lucide ListFilter. Everything else in this module is drawn from the 33 already shipped. Facet controls carry words, not pictures — a genre has no icon anybody can read. Dev handoff.

PieceNote

The job is to end the search — and the measure of it is how rarely somebody has to type twice.
