# Plan — harden, cut API calls, make it modular

**Approved by the owner, 2026-09-13.** Follows `docs/AUDIT_2026-09-13.md`.
Phases run in order. Each ends with a review before the next starts.
Phase D (per-module UX work) is **deferred**: the goal for now is a modular
codebase, not improved modules.

## Owner's intent, in his words

> "Think of it like SDK: login could be an SDK and I can add it wherever I
> want with some business rules and logics."

A module is therefore: a folder with a **public surface** (`index.js`),
internals nobody else imports, dependencies only on `shared/` and other
modules' public surfaces, and business rules passed in rather than baked in.

## Phase B — Cut TMDB calls *(1 day)*

Measured before the work (signed in, cold loads): Discover 4 · Search 6 per
query · Title 1–2 · Person 1 · **You 12** · Discover→title→back **5**.
A five-minute session is ~30 calls, nearly all re-fetching unchanged data.

| # | Item | Expected |
|---|---|---|
| B1 | Session cache in the TMDB transport: memoise GET by URL with a TTL, dedupe in-flight | every back-navigation refetch gone; −40–60 % per session |
| B2 | Cache each person's filmography totals in `catalog_people` (fill-when-absent, like season runtimes) | You 12 → 0 on repeat visits; Search's credit fetches share it |
| B3 | `/search/multi` on the unfiltered search path | Search 3 → 1 |
| B4 | Path-based edge TTLs in the proxy: titles for hours, trending for a minute | fewer TMDB-side calls across devices |
| B5 | Re-run the same measurement; record before/after in this document | numbers, not claims |

Deferred: bundling Discover's four feeds server-side (mostly a latency win).

### Phase B — measured, 2026-09-13

Distinct `/api/tmdb` requests per journey, signed in, same test account, same
browser. "Cold" is a full page load; "warm" is the same journey again in the
same session or after the caches have filled.

| Journey | Before | After (cold) | After (warm) | What changed |
|---|---|---|---|---|
| Cover | 1 | 1 | 1 | — |
| Discover | 4 | 4 | **0** | B1: rails cached for 5 min |
| Discover → title → **back** | **5** | **1** | 1 | B1: only the title is new |
| Search "zimmer" | **6** | **4** | **1** | B3: one `/search/multi` instead of three; B2: people's totals cached after first sight |
| Search "nolan" (people never seen before) | 6 | 4 | 1 | as above — the first sight stores them |
| Title (series) | 2 | 2 | 0 | B1 |
| Person | 1 | 1 | 0 | B1 |
| **You** | **12** | **12 once, then 0** | **0** | B2: totals stored on the person row; 12 people stored on first visit, none asked for since |
| Library, Settings | 0 | 0 | 0 | — |

The five-minute session that cost ~30 requests before now costs about 10 on a
cold start and about 3 warm.

**Edge cache (B4):** entity responses — a film, a series, a person, a season —
now carry `s-maxage=3600, stale-while-revalidate=86400`; feeds and searches
keep `60/300`. Not measurable from one browser; it reduces what TMDB sees
across devices and days.

**Search quality (B3), measured with the eval harness** on the 40 labelled
queries, direct to TMDB, no cache:

| | v1 baseline (50 q, 2026-09-11) | v2 (40 q, 2026-09-13) |
|---|---|---|
| null-and-low@5 | 52 % | 47.5 % |
| NDCG@10 | 0.47 | 0.50 |
| MRR | 0.47 | 0.50 |
| typo category n&l@5 | — | 95 % (18/19) |

Different query counts, so directional only: v2 is the same or slightly better
on exact and partial titles, and — as expected — no better on typos, because
`/search/multi` adds no typo tolerance. That remains the search module's own
work. Run saved as `eval/runs/2026-09-13T16-32-18-006Z__v2.json`.

**Found and fixed while measuring:** the people-results cache lookup had a
race — when a new list of people arrived, the previous answer was still in
state for one render, so every row asked TMDB before the real lookup landed.
Three needless requests per search, invisible on a slow network.

### Phase C — what was done, 2026-09-13

C0–C3 are complete. **C4 is not started** — it adds a dependency, so it is the
owner's call (see below).

**How "move, don't rewrite" was proven.** `main` was checked out into a second
worktree and served on port 5175 beside the branch on 5174. Every screen was
compared element by element — tag, position, size, for every node under `.app`
— and hashed. Identical on both servers:

| screen | width / theme | elements | hash |
|---|---|---|---|
| discover | 390 dark | 581 | `74360691` |
| search | 390 dark | 107 | `1e7ca95c` |
| you | 390 dark | 452 | `5a521452` |
| you | 1280 light | 452 | `471faf04` |
| person | 900 dark | 110 | `2489b840` |
| title | 900 dark | 295 | `ab8a507f` |
| title | 390 dark / 1280 light | 282 / 227 | `c8bffb16` / `c1deb497` |
| library | 1280 light | 52 | `64887061` |
| cover | 390 dark | 29 | `9bba3eab` |

**Two bugs the work surfaced, both pre-existing:**

- `.title-head` — the class the title page's loading skeleton draws — had no
  layout rule anywhere. Only the shimmer selector mentioned it, which is why
  "every class has a rule" never caught it. Since the Milestone 1 rebuild the
  poster and title stacked while loading and jumped sideways on arrival, which
  is what the design's "skeletons mirror the layout that's coming" rule exists
  to prevent.
- Carving the cross-cutting breakpoints out of `base.css` put the shell's media
  blocks *above* the rules they override. `.topbar { display: none }` and
  `.topbar { display: block }` at 1120 have equal specificity, so the second
  wins — and for one build, at 1280, the phone's tab bar showed while the
  desktop top bar stayed hidden. Caught by the library screen's fingerprint
  differing from main; `shell.css` now ends with its breakpoints and says why.

**What the checks became.** `npm run verify` grew from five to eight:

6. no inline styles outside `Skeleton` — and only for properties that carry
   data (width, height, backgroundImage, aspectRatio, transform), never a
   literal;
7. a module's **own** classes are used only by that module — a class the shared
   layer already defines may be scoped inside a module's element, because that
   is styling its own composition rather than claiming a primitive;
8. a module is imported from outside only through its `index.js`.

Checks 7 and 8 are what make a module an SDK rather than a folder.

### C4 — needs a decision

A Playwright script writing per-module screenshots at 390 / 900 / 1280 in both
themes, so a module's PR carries its own before-and-after. It means adding
Playwright as a devDependency (which downloads a browser, ~150 MB).

The alternative is the geometry fingerprint used above, which needs the same
browser to automate. Either way the dependency is the decision. Recommended:
take it — per-module UX work is exactly when it pays — but it is the owner's
call, and nothing in Phase D is blocked on it.
